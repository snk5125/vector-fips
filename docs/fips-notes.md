# FIPS notes — Vector 0.57.0 custom build (image started 2026-07-23)

How this image gets a *statically linked* OpenSSL to do all of its
cryptography in Red Hat's CMVP-validated FIPS provider, what was verified,
and where the compliance boundary actually sits.

## The mechanism

Vector's GA builds (and this build) link OpenSSL statically via the
`openssl/vendored` cargo feature → `openssl-src` pinned to the **3.0.x**
branch — the same branch as Red Hat's validated 3.0.7 provider module.
Static *libcrypto* does not mean static *providers*: since OpenSSL 3,
providers are loaded at runtime with `dlopen`, and the embedded libcrypto
honors `OPENSSL_CONF` and `OPENSSL_MODULES`. The binary is deliberately a
*dynamic glibc executable* (build-gated) so `dlopen` works; a musl-static
build could never load the provider.

The image wires it fail-closed
([config/openssl-fips.cnf](../config/openssl-fips.cnf)):

- `OPENSSL_MODULES=/usr/lib64/ossl-modules` — providers come from the
  **container** (Red Hat's `openssl-fips-provider-so` package), not from
  anything compiled into the binary.
- Providers activated: `fips` + `base` only. `base` contains encoders /
  decoders / store loaders (no cryptography); every algorithm
  implementation comes from `fips.so`.
- `[algorithm_sect] default_properties = fips=yes` — algorithm fetches
  demand FIPS-approved implementations; there is no silent fallback path.
- `config_diagnostics = 1` — a missing or broken provider fails libcrypto
  initialization loudly instead of continuing without FIPS.
- `[fips_sect]` is Red Hat's own `/etc/pki/tls/fips_local.cnf` (activate +
  `tls1-prf-ems-check`), included so provider options track the base image.

`VECTOR_FIPS=0` (dev only) makes the entrypoint drop `OPENSSL_CONF`.

## What is verified, every build

Build gates (Containerfile / ci/compile-in-container.sh):

- Source = pinned tag AND commit sha; toolchain + protoc sha256-pinned.
- The resolved dependency graph contains **zero** crates from
  [ci/forbidden-crates.txt](../ci/forbidden-crates.txt) (ring, aws-lc,
  rustls, RustCrypto primitives, dalek curves, ...). The graph itself ships
  in the image (`/usr/share/vector/build/cargo-tree.txt`).
- `ldd`: no dynamic `libssl`/`libcrypto` (OpenSSL is the vendored static
  one), but the executable is dynamic (provider dlopen possible).
- The system openssl CLI under the image's config activates `fips` + `base`.
- Spot removals: a VRL program calling `md5()` fails to compile; an
  `aws_s3` sink is an unknown type.

Runtime validation (ci/validate.sh):

1. **Positive**: with fips-only providers + `fips=yes` properties, the
   aggregator terminates a TLS 1.2/1.3 handshake (RSA-2048/SHA-256 cert
   generated by the image's own openssl under the same config) and the
   ingested event reaches a sink.
2. **Negative (non-vacuous)**: identical run with `OPENSSL_MODULES` pointed
   at a nonexistent directory must NOT serve TLS — proving assert #1
   depends on the container's `fips.so`, not on crypto baked into the
   binary.
3. **Provenance**: the runtime-active provider version string must equal
   the `io.grimoire.fips.provider.module-version` label pinned by
   [Containerfile.base](../Containerfile.base).
4. **Removals are real**: `vector validate` rejects `md5`/`sha2`/`encrypt`/
   `hmac`/`dns_lookup` VRL programs and `aws_s3`/`nats`/`websocket`/`mqtt`/
   `databend` components, while a control config using kept functions
   passes.

## Provider certificate lineage

Identical posture to the sibling `aggregator-fips` image (same base, same
pins): Red Hat ships the validated module as the frozen
`openssl-fips-provider-so` package, decoupled from routinely-patched
`openssl-libs`. **NIST CMVP certificate #4857** covers module
`3.0.7-395c1a240fbfffd8`; the image ships Red Hat's `-11.el9_8` rebuild
(module `3.0.7-cda111b5812c30d4`, fixing CVE-2026-31790 *in the provider*),
the only build UBI repos carry — certificate applies by lineage per Red
Hat's [compliance matrix](https://access.redhat.com/compliance/fips) while
revalidation is in process. The exact package NVR and embedded module
version are asserted at base build; a Red Hat provider bump fails the
weekly base pipeline until certificate status is reviewed and the pins are
updated in the same commit.

## Compliance caveats

- **Host kernel**: Red Hat's formal FIPS 140-3 posture requires the host to
  run `fips=1`. This image activates the validated provider regardless of
  host state; for a real compliance boundary run it on a FIPS-mode host.
- **Provider/libcrypto pairing**: the validated module is loaded by the
  *vendored upstream* libcrypto 3.0.x, not Red Hat's patched libcrypto it
  normally pairs with. The provider API is the stability boundary OpenSSL
  defines, and the functional + negative validation exercises the pairing
  every build — but an assessor may still care about the distinction;
  it is documented here deliberately.
- **EMS**: `tls1-prf-ems-check` is inherited from Red Hat's
  `fips_local.cnf` — TLS 1.2 key derivation requires extended master
  secret, per FIPS 140-3 IG.
- **Randomness**: Vector uses OS randomness / `rand` for non-cryptographic
  purposes (UUIDs, sampling, backoff jitter). These are not cryptographic
  services and are not routed through the provider's DRBG; TLS session
  crypto (the cryptographic service this image provides) draws from the
  FIPS provider.
- **lto deviation**: upstream GA releases build with `lto = "fat"`; this
  image builds with thin LTO (builder RAM ceilings). Performance-only —
  same code, same dependency graph.
- **kafka/SASL**: built without `gssapi` (like upstream's local-dev
  default) — Kerberos SASL is unavailable; TLS + SASL/PLAIN-over-TLS paths
  go through librdkafka's OpenSSL, which links the same vendored libcrypto
  and therefore the FIPS provider.
